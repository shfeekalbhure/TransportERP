- دعم تعدد الشركات والفروع.
- تقليل أخطاء المستخدم.
- رفع كفاءة العمل.

## 1.3 فلسفة النظام

- البساطة.
- الوضوح.
- الكفاءة.
- القابلية للتوسع.
- المرونة.

## 1.4 نطاق التطبيق
يطبق هذا الدليل على جميع واجهات النظام.

## 1.5 أولوية المراجع
1. دليل التصميم الموحد.
2. سجل القرارات.
3. مسودة الكراسة.
4. كراسة الشاشات.
5. الصور المعتمدة.

## 1.6 مبدأ التوحيد
أي عنصر يتكرر في أكثر من شاشة يجب أن يكون له تصميم وسلوك موحد.

## 1.7 مبدأ التحليل قبل التصميم
لا يبدأ التصميم قبل اكتمال تحليل الشاشة.

## 1.8 مبدأ الاعتماد
لا تعتبر أي شاشة معتمدة إلا بعد مطابقة هذا الدليل.

## 1.9 لا اجتهاد في العناصر الموحدة
لا يجوز تغيير العناصر القياسية إلا بقرار رسمي.

# القرار التنظيمي رقم UI-DOC-001
## تنظيم وثائق وتصاميم شاشات TransportERP حسب المجموعات والشاشات

**الحالة:** معتمد  
**تاريخ الاعتماد:** 2026-08-06  
**النطاق:** جميع أعمال تحليل وتصميم وتوثيق شاشات TransportERP.

## 1. الهدف
تنظيم جميع وثائق وتحليلات وتصاميم الشاشات داخل هيكل واحد واضح، بحيث تكون كل مجموعة وظيفية في مجلد مستقل، وكل شاشة في مجلد مستقل داخل مجموعتها، مع منع خلط ملفات المجموعات أو تكرار الصور والوثائق.

## 2. موقع المرجع الأعلى
يوضع دليل التصميم الموحد في:

```text
Documentation/UI-Design/00-Standards/
```

ويكون هذا المجلد مرجعًا مشتركًا لجميع المجموعات، ولا يتبع أي مجموعة وظيفية.

## 3. الهيكل الإلزامي

```text
Documentation/
└── UI-Design/
    ├── 00-Standards/
    │   ├── دليل_التصميم_الموحد_لواجهات_TransportERP.md
    │   ├── AGENTS.md
    │   └── سجل_القرارات_المعتمدة.md
    ├── 01-Geographic/
    ├── 02-General-Setup/
    ├── 03-Security-Administration/
    ├── 04-Accounting/
    └── 05-Budget-Financial-Control/
```

## 4. ملف المجموعة
يجب أن يحتوي مجلد كل مجموعة على ملف رئيسي باسم:

```text
كراسة_مجموعة_<اسم_المجموعة>.md
```

ويتضمن تعريف المجموعة ونطاقها، قائمة الشاشات والتبويبات، القواعد المشتركة، ترتيب العمل، حالة كل شاشة، ما تم وما تبقى، روابط الملفات والصور، والنواقص والتعارضات المفتوحة.

## 5. مجلد الشاشة

```text
<Screen-Code>-<Screen-Name>/
├── README.md
├── تحليل_الشاشة.md
├── مواصفات_الحقول.md
├── اختبارات_القبول.md
├── سجل_النواقص.md
└── Designs/
```

## 6. تنظيم الصور
- تحفظ صورة مستقلة لكل تبويب.
- الصور غير المعتمدة توضع في `Drafts`.
- الصور المعتمدة فقط توضع في `Approved`.
- تحمل الصورة رمز الشاشة ورمز التبويب.
- لا تجمع عدة تبويبات في صورة واحدة.

## 7. قواعد التجميع
- الشاشات المتشابهة وظيفيًا وأدائيًا توضع داخل المجموعة نفسها.
- لا تدمج تفاصيل عدة شاشات داخل ملف شاشة واحد.
- القواعد المشتركة توثق في ملف المجموعة أو الدليل الموحد.
- الخصائص الخاصة توثق داخل ملف الشاشة المعنية.

## 8. ترتيب المراجع داخل كل ملف مجموعة
يبدأ كل ملف مجموعة بالنص التالي:

> يجب قراءة وتطبيق دليل التصميم الموحد وسجل القرارات المعتمدة قبل تحليل أو تصميم أو تعديل أي شاشة في هذه المجموعة.

## 9. حالات العمل الموحدة
- لم تبدأ.
- قيد التحليل.
- التحليل مكتمل.
- قيد التصميم.
- تحتاج استكمالًا.
- قيد المراجعة.
- معتمدة بصريًا.
- جاهزة للتنفيذ.
- منفذة برمجيًا.
- تحتاج تصحيحًا.

## 10. منع الادعاء غير الصحيح
لا تعتبر الشاشة منفذة أو معتمدة لمجرد وجود صورة أو ملف؛ بل يجب تحديث حالتها صراحةً في ملف المجموعة بعد اجتياز التحليل والمراجعة والاعتماد.

## 11. التطبيق
يطبق هذا القرار على جميع المجموعات الحالية والمستقبلية، ويصبح مرجعًا إلزاميًا لأي مساعد ذكاء أو مصمم أو محلل أو مطور يعمل على المشروع.

# القرار التنفيذي رقم UI-EXEC-002
## استثناء تنفيذ شاشات WinForms من بيئة المستودع

**الحالة:** معتمد  
**تاريخ الاعتماد:** 2026-08-07  
**النطاق:** جميع شاشات `TransportERP.Desktop` التي يصدر بشأنها تكليف تنفيذ صريح داخل المستودع.

## 1. الأصل
يبقى التنفيذ المحلي على Windows بواسطة `Windows Forms Designer` و`Toolbox` و`Properties Window` هو الأسلوب الأصلي والمفضل عندما تكون هذه الأدوات متاحة.

## 2. الاستثناء المعتمد لبيئة المستودع
إذا كان المساعد يعمل مباشرة داخل مستودع Git ولا تتوفر له بيئة Visual Studio أو Windows Forms Designer أو Toolbox أو Properties Window، فيُسمح له صراحةً بإنشاء وتعديل ملفات WinForms التالية مباشرة:

- `.cs`
- `.Designer.cs`
- `.resx`

ولا يعد هذا مخالفة لقرار استخدام Windows Forms Designer متى كان التكليف التنفيذي الصريح يطلب العمل داخل المستودع.

## 3. شروط التنفيذ المباشر
يلزم عند التنفيذ المباشر داخل المستودع ما يلي:

1. تكون الملفات الناتجة بصيغة WinForms القياسية وقابلة للفتح لاحقًا في Windows Forms Designer.
2. كل Control ثابت له `field declaration` صريح مستقل.
3. كل Control ثابت يُنشأ مباشرة داخل `InitializeComponent()`.
4. يمنع إنشاء العناصر الثابتة بواسطة متغيرات محلية مؤقتة أو Helper Methods جماعية إذا كان ذلك يمنع ضبط خصائص كل عنصر ومراجعته بصورة مستقلة.
5. تطبق خصائص الـForm والحاويات والأدوات والمقاسات والاتجاه والترتيب حرفيًا وفق المسودة والكراسة والمخطط المعتمد.
6. يمنع التخمين؛ أي خاصية أو عنصر أو تبويب أو عمود غير محدد في المرجع يسجل: `غير محددة في المرجع` ولا يُنشأ من الاجتهاد.
7. يظل الاتجاه العربي الحاكم: `RightToLeft = Yes` و`RightToLeftLayout = True`، وتبدأ الأدوات من جهة اليمين وفق المرجع.
8. لا يسمح بتغيير المقاسات أو الحاويات أو ترتيبها لمجرد تسهيل كتابة الكود.
9. لا يضاف منطق أعمال أو API أو قاعدة بيانات أو خدمات إلا إذا ورد تكليف مستقل بذلك.
10. عند توفر Visual Studio لاحقًا، يجب التحقق من فتح الشاشة في Designer دون أخطاء.

## 4. أولوية هذا القرار عند التعارض
عند وجود نص سابق في المسودة أو الكراسة أو المخطط يقول إن إنشاء الشاشة يجب أن يتم حصريًا من Windows Forms Designer، يُفسر ذلك النص على أنه الأسلوب الأصلي عند توفر بيئة Visual Studio، ولا يجوز استخدامه لإيقاف مهمة تنفيذ صريحة داخل المستودع.

هذا القرار يرفع المنع الناتج فقط عن عدم توفر Designer/Toolbox/Properties Window، ولا يلغي أي مواصفة تصميمية أخرى في الإصدار 1.13.

## 5. قاعدة عدم التوقف
عندما يصدر تكليف صريح بالتنفيذ داخل المستودع، لا يجوز للمساعد إيقاف التنفيذ لمجرد عدم توفر Windows Forms Designer. يجب عليه استخدام الاستثناء المعتمد وتنفيذ الملفات مباشرة مع الالتزام الكامل بالمراجع وعدم التخمين.
