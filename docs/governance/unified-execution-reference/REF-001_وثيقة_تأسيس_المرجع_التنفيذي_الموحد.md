# REF-001 — وثيقة تأسيس المرجع التنفيذي الموحد لمشروع TransportERP

## 1. الحالة

**وثيقة تأسيس حاكمة لإدارة المرجع التنفيذي الموحد**.

هذه الوثيقة لا تعتمد قاعدة بيانات، ولا تعتمد كراسة جديدة بصفتها `Current Approved — الحالي المعتمد`، ولا تمنح `Implementation Authorization — تصريح التنفيذ البرمجي`.

هدفها إنشاء مسار واحد منضبط لبناء **المرجع التنفيذي الموحد لمشروع TransportERP** من جميع مصادر المشروع الصحيحة، مع حفظ الأثر التاريخي ومنع التكرار والتعارض والاعتماد الصامت.

## 2. الاسم الرسمي

**المرجع التنفيذي الموحد لمشروع TransportERP**

`Unified Project Execution Reference — المرجع التنفيذي الموحد للمشروع`.

عند اكتماله واعتماده من السلطة المخولة يصبح المرجع التنفيذي الأعلى للمشروع ضمن نطاقه، وتبقى المصادر الأصلية محفوظة كأثر ومراجع حاكمة أو تاريخية بحسب تصنيفها.

## 3. المبادئ الحاكمة

1. **لا حذف أثناء مرحلة الاكتشاف والتهيئة.**
2. **لا ترقية صامتة.** أي ملف جديد لا يصبح `Current Approved — الحالي المعتمد` لمجرد أنه أحدث تاريخًا.
3. **لا دمج من الاسم فقط.** التكرار يفحص بالبصمة والمحتوى والدلالة والسلطة.
4. **لا إسقاط للمصدر.** كل معرفة تدخل المرجع يجب أن تعود إلى `Source ID — معرف المصدر` واضح.
5. **قرارات المالك الحاكمة أعلى من المصادر الأدنى في نطاقها.**
6. **المصدر المعتمد الحالي لا يهزم بمسودة أو بحث أو مرشح تطوير.**
7. **المعمارية المشتقة توسم كمشتقة.** لا يعاد وصف الاستنتاج اللاحق على أنه موجود تاريخيًا في المصدر.
8. **البحث العالمي لا يرقّى تلقائيًا إلى متطلب.** يسجل أولًا كـ`Benchmark Candidate — مرشح مقارنة` أو `Development Proposal — مقترح تطوير` حتى اعتماد قرار التبني.
9. **الأدلة لا تصبح قواعد أعمال.** نتائج `POC — إثبات المفهوم` والسجلات التشغيلية والصور تثبت حالة أو اختبارًا ولا تنشئ قاعدة أعمال بذاتها.
10. **كل مصطلح تقني إنجليزي في الوثائق التنفيذية يتبعه تفسير أو ترجمة عربية مباشرة.**

## 4. منهج البحث الإلزامي

يجب أن يكون العمل `Deep Research — بحثًا عميقًا` وليس مراجعة عناوين.

### 4.1 البحث الداخلي

يشمل `File Library — مكتبة الملفات` كاملة لمواد TransportERP، مع إعطاء أولوية خاصة للتسلسل منذ 8 أغسطس 2026 وحتى أحدث عنصر متاح.

يفحص المحتوى الفعلي: الملفات، الصفحات، الصفوف، الشاشات، التبويبات، الحقول، الإجراءات، الحالات، الصلاحيات، العقود، الجداول، العلاقات، الصور، الأدلة، المراجعات، الحزم، وسجلات البصمات.

### 4.2 البحث الخارجي

يستخدم `Primary Sources — المصادر الأولية` و`Official Sources — المصادر الرسمية` للأنظمة والشركات الكبرى ذات العلاقة بـ:

- `ERP — تخطيط موارد المؤسسات`.
- `TMS — إدارة النقل`.
- `WMS — إدارة المستودعات`.
- المحاسبة والمالية.
- النقل والشحن والركاب والتذاكر.
- التوصيل وآخر ميل.
- الأساطيل والصيانة.
- `GPS / Telematics — تحديد المواقع والقياس عن بعد`.
- الجوال والعمل دون اتصال.
- الأمن والحوكمة والتكاملات.

المصادر الخارجية تستخدم لكشف الفجوات والمقارنة والتحسين، ولا تهزم مصدرًا حاكمًا للمشروع دون قرار تبنٍ صريح.

## 5. تصنيف المصادر

يستخدم المرجع سبع فئات على الأقل:

1. `GOVERNING_CURRENT — حاكم حالي`: مصدر معتمد حاليًا في نطاقه.
2. `PRESERVED_SOURCE — مصدر محفوظ`: معنى أعمال محفوظ مع تتبع، يدخل بشرط عدم مخالفة الحاكم الأعلى.
3. `DERIVED_ARCHITECTURE — معمارية مشتقة`: استنتاج أو طبقة ربط لاحقة تدخل مع وسم الاشتقاق والثقة والمراجعة.
4. `BENCHMARK_CANDIDATE — مرشح مقارنة`: بحث عالمي أو إثراء؛ لا يدخل كحكم قبل قرار تبنٍ.
5. `EVIDENCE_ONLY — دليل فقط`: اختبار أو مراجعة أو صورة أو سجل تشغيل؛ لا ينشئ قاعدة أعمال.
6. `HISTORICAL_SUPERSEDED — تاريخي/مستبدل`: يحفظ للتدقيق ولا يستخدم للتنفيذ عند وجود بديل أعلى معتمد.
7. `QUARANTINED_CONFLICT — محجور/متعارض`: لا يدخل التنفيذ حتى حسم الهوية أو السلطة أو التعارض.

## 6. السلم الهرمي للعمل

### المرحلة 1 — تهيئة المستودع

- فحص المستودع كما هو.
- توثيق بنيته الحالية دون تغيير جوهر الكود.
- إنشاء مساحة الحوكمة للمرجع التنفيذي الموحد.
- إنشاء سجل مسؤولية التنفيذ.
- إنشاء تقرير تهيئة أولي.
- عدم حذف أو نقل كود قائم في هذه المرحلة.

### المرحلة 2 — جرد المكتبة وتصنيفها

- جرد جميع أصول TransportERP ذات العلاقة.
- حساب/تسجيل البصمات حيث تتوفر.
- تحديد النسخ المكررة والمتعارضة والمستبدلة.
- إعادة بناء خط النسب الوثائقي من 8 أغسطس 2026 حتى أحدث حالة.
- تحديد `Working Set — مجموعة العمل` الصحيحة.

### المرحلة 3 — تجميد سلطة المصادر

- إنشاء `Source Authority Register — سجل سلطة المصادر`.
- تحديد الحاكم الحالي في كل مجال.
- ربط كل مرشح أو مصدر محفوظ بمصدره الأعلى.
- منع استخدام النسخ المؤرشفة عند وجود نسخة معتمدة أحدث.

### المرحلة 4 — بناء نواة المرجع الموحد

- دمج المعرفة الصحيحة لا نسخ الملفات آليًا.
- إنشاء السجلات الموحدة للشاشات والحقول والإجراءات والبيانات والعقود والتقارير.
- الحفاظ على معرفات المصدر والتتبع.

### المرحلة 5 — المراجعة الدلالية العميقة

المراجعة تكون بالتسلسل:

ملفًا ملفًا، صفحة صفحة، صفًا صفًا، شاشة شاشة، تبويبًا تبويبًا، حقلًا حقلًا، إجراءً إجراءً، حالة حالة، صلاحية صلاحية، قاعدة عمل قاعدة عمل، علاقة علاقة، وعقدًا عقدًا.

### المرحلة 6 — البحث العالمي والإثراء

- مقارنة TransportERP بالأنظمة العالمية الرسمية ذات الصلة.
- تسجيل كل تحسين كمرشح منفصل.
- عدم إدخاله في المتطلبات الحاكمة بلا قرار تبنٍ.

### المرحلة 7 — إغلاق الفجوات والتعارضات

- معالجة ما تسمح به السلطة.
- رفع `Owner Decision Required — يتطلب قرار المالك` لما لا يمكن حسمه من المصادر.
- تحديث سجل التغييرات والتتبع بعد كل معالجة.

### المرحلة 8 — الاختبارات والأدلة

الهدف النهائي:

`Requirement → Contract → Test → Evidence — المتطلب → العقد → الاختبار → الدليل`.

لا يقبل `PASS — نجاح` وصفي بلا دليل تنفيذي أو مراجعة مستقلة عندما يتطلب الأمر ذلك.

### المرحلة 9 — المراجعة المستقلة النهائية

تجمد حزمة المرشح وتسلّم إلى جهة ضمان مستقلة. لا يصبح المرجع `Current Approved — الحالي المعتمد` إلا بقرار السلطة المخولة بعد المراجعة.

## 7. قواعد تنظيم الملفات

- لا ينشأ إصدار جديد لكل تعديل صغير.
- توجد `Active Working Set — مجموعة عمل نشطة` واحدة لكل مرحلة.
- التعديلات اليومية تسجل في `Change Log — سجل التغييرات`.
- الإصدار المجمد ينشأ عند إغلاق مرحلة أو تسليم مراجعة أو اعتماد.
- التكرار الحقيقي لا يحذف في مرحلة الاكتشاف؛ يصنف أولًا.
- `Same Name / Different SHA — الاسم نفسه ببصمة مختلفة` يعامل كتعارض هوية حتى الحسم.
- `Same SHA / Different Name — البصمة نفسها باسم مختلف` يعامل كمرشح نسخة مطابقة مع حفظ المواقع والعلاقات.

## 8. علاقة المستودع بالمكتبة

`GitHub Repository — مستودع جيت هب` هو المصدر الحاكم للكود ومخرجات الحوكمة النصية الخاصة بالكود.

`File Library — مكتبة الملفات` هي مساحة أصول المشروع غير البرمجية: الكراسات، السجلات، الأدلة، الصور، الحزم، المراجعات، والبحوث.

لا تكرر ملفات المكتبة الضخمة داخل المستودع. يوضع بدلًا منها فهرس ومعرفات ومسارات وبصمات ومراجع تتبع.

## 9. حالة قاعدة البيانات

`Database Platform Final Selection = OPEN — الاختيار النهائي لمنصة قاعدة البيانات = مفتوح`.

`PostgreSQL 18.x = Preferred Candidate — بوستجري إس كيو إل 18.x = المرشح المفضل`.

`MySQL = Active Comparator — ماي إس كيو إل = المنافس الفعلي`.

`Implementation Authorized = NO — التنفيذ البرمجي = غير مصرح بموجب هذه الوثيقة`.

أي رسم أو وصف يستخدم PostgreSQL يجب أن يوسم:

`Conditional Target Architecture — معمارية مستهدفة مشروطة بنتيجة POC-14`.

## 10. عقود معمارية ثابتة في مرحلة القرار

- `Database Replication ≠ TransportERP Business Synchronization — نسخ قاعدة البيانات لا يساوي مزامنة أعمال TransportERP`.
- `At-Least-Once Delivery + Idempotent Business Effect — تسليم مرة واحدة على الأقل مع أثر تجاري غير متكرر`.
- `Offline-First — العمل دون اتصال أولًا` متطلب جوهري، لكن تفاصيل السلطة المحلية والمزامنة تبقى مرتبطة بالعقود والمراجعات الحاكمة.

## 11. بوابات الجودة قبل وصف المرجع بالمكتمل

لا يوصف المرجع بأنه مكتمل حتى يتحقق على الأقل:

- `File Coverage = 100% — تغطية الملفات = 100%` ضمن النطاق المجمد.
- `Screen Coverage = 100% — تغطية الشاشات = 100%`.
- `Field Coverage = 100% — تغطية الحقول = 100%`.
- `Action Coverage = 100% — تغطية الإجراءات = 100%`.
- فجوات التتبع الحرجة = صفر.
- التعارضات المانعة غير المحسومة = صفر.
- الأصول الحاكمة غير المحسوبة = صفر.
- مراجعة مستقلة للحزمة المجمدة = مكتملة.

## 12. حدود هذه الوثيقة

هذه الوثيقة تؤسس عملية بناء المرجع فقط.

لا تمنح:

- اعتمادًا نهائيًا للكراسة.
- اعتمادًا نهائيًا لقاعدة البيانات.
- تصريحًا بالبرمجة.
- تصريحًا بالترحيل.
- تصريحًا بحذف الملفات التاريخية.
