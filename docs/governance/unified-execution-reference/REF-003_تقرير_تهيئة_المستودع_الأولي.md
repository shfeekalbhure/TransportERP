# REF-003 — تقرير تهيئة المستودع الأولي لمشروع TransportERP

## 1. نطاق الفحص

تم فحص مستودع:

`shfeekalbhure/TransportERP — مستودع TransportERP`.

وتمت مراجعة البنية الفعلية للفرع الافتراضي `master — الفرع الرئيسي` قبل إنشاء مساحة الحوكمة الجديدة.

## 2. الحالة الفعلية قبل التهيئة

آخر حالة أساس مرصودة على الفرع الرئيسي كانت Commit — التزامًا بعنوان:

`Reset repository to empty project structure — إعادة ضبط المستودع إلى هيكل مشروع فارغ`.

وهذا يتفق مع المحتوى الحالي: المستودع يمثل **هيكل حل أولي** أكثر من كونه تنفيذًا وظيفيًا مكتملًا.

## 3. المشاريع الموجودة في الحل

ملف `TransportERP.slnx — ملف الحل` يسجل عشرة مشاريع:

1. `TransportERP.Api — واجهة البرمجة`.
2. `TransportERP.Application — طبقة التطبيق`.
3. `TransportERP.Contracts — العقود`.
4. `TransportERP.Desktop — تطبيق سطح المكتب`.
5. `TransportERP.Infrastructure — البنية التحتية`.
6. `TransportERP.Mobile.Admin — جوال الإدارة`.
7. `TransportERP.Mobile.Customer — جوال العميل`.
8. `TransportERP.Mobile.Driver — جوال السائق`.
9. `TransportERP.Tests — الاختبارات`.
10. `TransportERP.Domain — المجال`، وملفه موجود فعليًا تحت المسار `TransportERP/TransportERP.Domain.csproj`.

## 4. الملاحظة الهيكلية الرئيسية

أسماء تسعة مجلدات تطابق أسماء المشاريع مباشرة، بينما مشروع `TransportERP.Domain — المجال` موضوع داخل مجلد اسمه `TransportERP` بدل `TransportERP.Domain`.

لا يتم تغيير هذا المسار في مرحلة التهيئة الأولى، لكنه يسجل كملاحظة تنظيمية تحتاج قرارًا لاحقًا قبل أي إعادة تسمية، لأن إعادة التسمية قد تؤثر على الحل والمراجع والبناء.

## 5. درجة الجاهزية الحالية

الحكم الأولي:

`REPOSITORY STRUCTURAL SHELL — المستودع هيكل إنشائي أولي`.

وليس:

`IMPLEMENTATION-READY REPOSITORY — مستودع جاهز للتنفيذ الكامل`.

السبب: الشجرة الحالية المعروضة تتكون أساسًا من ملفات المشاريع وملف الحل، ولا تحتوي في خط الأساس الذي تمت مراجعته على هيكل حوكمة موثق أو مرجع تنفيذي موحد داخل المستودع.

## 6. ما تم تنفيذه في مرحلة التهيئة

تم إنشاء فرع عمل مستقل:

`governance/unified-execution-reference-foundation — حوكمة/تأسيس المرجع التنفيذي الموحد`.

وتم إنشاء مساحة:

`docs/governance/unified-execution-reference — توثيق/حوكمة/المرجع التنفيذي الموحد`.

وإضافة:

- `REF-001 — وثيقة تأسيس المرجع التنفيذي الموحد`.
- `REF-002 — سجل مسؤولية التنفيذ`.
- هذا التقرير `REF-003 — تقرير تهيئة المستودع الأولي`.

لم يتم حذف أو نقل أو تعديل أي مشروع برمجي قائم ضمن هذه المرحلة.

## 7. نتائج فحص مكتبة المشروع المرتبطة بالتهيئة

مراجعة المكتبة الحالية للفترة من 8 أغسطس 2026 حتى 15 أغسطس 2026 أثبتت وجود عدة سلالات وثائقية، ولذلك لا يجوز بناء المرجع الموحد من ملف واحد بالاسم فقط.

الحالة التي يجب مراعاتها في مرحلة الجرد التالية:

- `Current Approved — الحالي المعتمد`: سلطة المصادر الحالية المشار إليها في سجل كراسة 8-8 وما يسميه من W1/W2/W3.
- `V4.1R2 — المعالجة V4.1R2`: أشمل نواة محتوى حالية، لكنها مرشح معالجة وليست ترقية تلقائية للحاكم الحالي.
- المصدر V3 محفوظ للمعنى والتتبع.
- طبقات `ARCH-01R — البحث/المراجعة المعمارية` تصنف كمعمارية مشتقة حيث ينطبق ذلك.
- البحث العالمي والأدلة البصرية مرشحات مقارنة وتحسين، وليست قواعد أعمال حاكمة تلقائيًا.
- أدلة `POC — إثبات المفهوم` ومسارات هيكل المشروع أدلة تنفيذ/حوكمة ولا تعيد تعريف قواعد الأعمال تلقائيًا.

## 8. أرقام خط الأساس الوثائقي التي تحتاج تحققًا مستمرًا

تقرير الاكتشاف الحالي في المكتبة سجل فحص 2,022 مدخل ملف/سجل ضمن النافذة الزمنية من 8 إلى 15 أغسطس 2026.

كما سجل نواة V4.1R2 التالية:

- 599 شاشة.
- 8,230 حقلًا.
- 6,282 إجراء/حالة/صلاحية.
- 255 مفهوم بيانات/جدول منطقي.
- 18,609 متطلبًا ذريًا ضمن مسار الحفظ والتتبع.

هذه الأرقام تستخدم كـ`Reconciliation Baseline — خط أساس للمطابقة` وليست تصريحًا بأن كل عنصر جاهز للتنفيذ.

## 9. العوائق المعروفة التي يجب ألا تضيع في الدمج

قبل وصف المرجع التنفيذي الموحد بأنه جاهز للتنفيذ، يجب إغلاق أو إعادة التحقق من البنود المعروفة، ومنها:

- الربط الدقيق لعقود `Posting — الترحيل`.
- الربط الدقيق لعقود `Reversal — العكس`.
- ربط `Screen → API → Permission — الشاشة → واجهة البرمجة → الصلاحية` بالمصادر الحالية الصحيحة.
- تثبيت `Field → Tab — الحقل → التبويب` و`Action → Area/Tab — الإجراء → المنطقة/التبويب` مع وسم الاشتقاق والثقة حيث كان الربط مشتقًا.
- إكمال `Offline / Sync — العمل دون اتصال / المزامنة` للعناصر التي لم يثبت سلوكها نهائيًا.
- استمرار الفصل بين اختيار قاعدة البيانات المرشح والقرار النهائي.

## 10. ممارسات المستودع المرجعية المقترحة

استنادًا إلى إرشادات GitHub الرسمية:

- استخدام `Rulesets — مجموعات قواعد الحماية` أو `Branch Protection — حماية الفروع` للفرع الرئيسي عند الانتقال من مرحلة التأسيس إلى العمل الجماعي الفعلي.
- استخدام `CODEOWNERS — ملف ملاك الكود` بعد تثبيت الأشخاص/الفرق الفعلية، لطلب مراجعة مالكي المسارات الحساسة.
- اشتراط `Pull Request Review — مراجعة طلب الدمج` والتدقيق قبل دمج المخرجات الحاكمة عندما تسمح خطة العمل بذلك.

لم يتم تفعيل هذه الإعدادات في هذا التقرير؛ هي توصيات تهيئة تحتاج تطبيقًا منفصلًا وفق صلاحيات المستودع والفرق الفعلية.

## 11. ما لا يجب فعله الآن

- لا إعادة تسمية للمشاريع.
- لا نقل للكود.
- لا حذف لملفات المكتبة أو المستودع.
- لا إدخال جميع ملفات المكتبة إلى GitHub.
- لا اعتماد V4.1R2 كحاكم أعلى تلقائيًا.
- لا اعتبار PostgreSQL قاعدة البيانات النهائية.
- لا بدء برمجة وظيفية بموجب هذه المرحلة.
