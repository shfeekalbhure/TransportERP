1. `REFERENCE VERSION CONFLICT — A11 FINGERPRINT`: الملف المحمّل من الهوية الحية المثبتة `file_000000001a7c81fd87469fb8c0e9fdf4` أعطى SHA-256 `0f6036b62901983f7ba72bbaf74559df513061e68bb530bacac22f711e9663d6`، بينما فهرس المراجع يصف هذه البصمة نفسها بأنها تاريخية فقط. اعتمدتُ `file_id + version 14 + المسار الحي` كهوية القراءة، ولم أستخدم البصمة المتعارضة لإثبات حداثة النسخة.
2. `GOVERNANCE DELTA — R-012 LOCATION`: مسار R-012 غير موجود في شجرة HEAD الجولة الأصلية، لكنه مثبت في الفهرس على commit حوكمة محدد وبـblob مطابق. تمت قراءته من ذلك commit دون نسخ الملف أو تعديل مرجع مشترك.

## 2. نطاق المراجعة وحدودها

### 2.1 داخل النطاق

- الطلب والحجز والاستقبال والفحص.
- البوليصة، الأصناف، الطرود، الرسائل والمنقولات.

- المخزن، التحميل، التفريغ، العهدة وسلسلة الحيازة.

### 2.2 خارج النطاق

- تسعير التعرفة والعمولات والقيد والتسوية المالية: ملك الفريق 05؛ تُرسل له المدخلات التشغيلية فقط.
- الهوية الحساسة، صلاحيات الوصول، قوة الأدلة، GPS/الخصوصية وسياسة الاحتفاظ: ملك الفريق 07.
- HR والصيانة العامة؛ استُخدم فقط قيد جاهزية السائق/المركبة والعطل المؤثر في رحلة قائمة.

### 2.3 حدود الإثبات

- A11 يثبت وجود معرفات وعناوين في المجتمع الحي، لكنه لا يثبت وحده فصل الشاشة أو اكتمال عقدها.

- R-005/R-006/R-007 تثبت احتياجات تشغيلية ومسودات توزيع، ولا تمنح Permission أو Action Contract.
- كل عمل دون اتصال يبقى وفق القسم 10، ولا يُستنتج من وجود تطبيق جوال أو كلمة Offline في اسم شاشة.

#### إضافة تصحيحية داخل دورة الشحن — دفتر البوالص الورقي (بلا ID جديد)

هذه الإضافة تستهلك إحالة الفريق 01 والمتطلب القائم في R-006، ولا تنشئ شاشة أو معرفًا جديدًا:

1. **تعريف الدفتر:** كل دفتر بوليصات ورقي يحتوي `50` ورقة متسلسلة.
2. **بدايات النطاقات:** تبدأ الدفاتر على النمط `1 / 51 / 101 / 151 ...`؛ وبالتالي يكون نطاق الدفتر محددًا من أول ورقة إلى الورقة الخمسين في ذلك النطاق.
3. **عهدة الدفتر:** عند تسليم دفتر إلى طرف تشغيلي، تسجل عهدة الدفتر ككل على الطرف المستلم حتى الإرجاع/المصالحة وفق الإجراء التشغيلي المعتمد.
4. **عهدة الورقة:** كل ورقة داخل الدفتر تبقى مرتبطة بعهدة الدفتر والطرف المسؤول عنها، ولا تنفصل مسؤوليتها لمجرد كونها غير مستخدمة.
5. **الورقة المتاحة:** ورقة داخل نطاق الدفتر لم تستخدم ولم تلغَ؛ صالحة للاستهلاك فقط ضمن عهدة ذلك الدفتر.
6. **الورقة المستخدمة:** عند استهلاكها في بوليصة، تحفظ كـ«مستخدمة» مع مرجع البوليصة/السجل المقابل، ولا تعاد إلى المتاح.
7. **الورقة الملغاة:** الإلغاء حالة صريحة تحفظ رقم الورقة وتسلسلها وتاريخ/سبب الإلغاء حسب السياسة اللاحقة؛ لا تمحى الورقة ولا يعاد استخدامها.
8. **منع تجاوز النطاق:** يمنع استهلاك رقم أقل من بداية الدفتر أو أعلى من نهايته، ويمنع القفز إلى نطاق دفتر آخر باعتباره جزءًا من نفس العهدة.
9. **العلاقة مع رقم النظام:** رقم الورقة الورقي ورقم النظام معرفان مرجعيان مختلفان يجب حفظ العلاقة بينهما؛ لا يحل أحدهما محل الآخر ولا يسمح النظام بفقد أي منهما عند التسجيل/المصالحة.
10. **المصالحة:** عند مراجعة الدفتر يجب أن يفسر كل رقم داخل نطاقه بأنه متاح أو مستخدم أو ملغى، وأي رقم غير مفسر يبقى فرق عهدة يحتاج معالجة، دون اختراع حالة نهائية أو سياسة مالية من الفريق 04.

### 4.2 التوصيل والنقل الخفيف

1. طلب Pickup/Delivery مع موقع مصرح ونافذة زمنية.
2. تحقق من نطاق الخدمة، حجم/وزن الطرد، المركبة والتوفر.
3. إسناد مندوب/سائق؛ الإسناد لا ينقل العهدة.
4. وصول المنفذ إلى Pickup؛ GPS قرينة وصول فقط.
5. مسح/عد/تصوير/قبول المنقول؛ هنا تبدأ العهدة الفعلية.
6. نقل مباشر أو عبر مركز/فرع.
7. محاولة تسليم مع OTP/توقيع/هوية حسب سياسة 07.
8. نجاح كلي/جزئي، أو تعذر/رفض.
9. إعادة محاولة أو RTO بقرار مسبب.
10. إخلاء عهدة المنقول والتحصيلات كلٌ في مساره.

## 5. نماذج الحالات والانتقالات

### 5.1 الطلب

`مسودة → مقدم → تحت المراجعة/الفحص → مؤهل للإصدار → صادر كبوليصة`.

فروع: يحتاج تأكيد عميل، معلق، مرفوض، ملغى.

الحارس: لا إصدار إذا بقي مانع فحص/تصريح/طرف/مسار/تسعير أو اعتماد مطلوب. قرار السماح بإصدار بعض الأنواع قبل اكتمال الفحص غير محسوم.

### 5.2 الوحدة المنقولة

`مصرح بها → مفحوصة → مستلمة مخزنيًا → مخصصة → محملة → مقبولة بعهدة السائق → أثناء النقل → وصلت → خرجت للتسليم → مسلمة`.

فروع: فرق، حجز، مقيدة، تحويل، تسليم جزئي، تعذر، RTO، تلف، نقص، فقد، إلغاء.

### 5.3 العهدة

`مع المرسل → مع المندوب/المكتب → مع المخزن → مع السائق/الناقل → مع فرع الوصول/مندوب التوصيل → مع المستلم`.

قاعدة الكمية: `المقبول للطرف التالي` فقط يخرج من عهدة الطرف الأول؛ المرفوض أو غير المطابق يبقى في عهدته أو في استثناء رسمي.

### 5.4 رحلة الشحن

`مخططة → مخصصة → تحت التجهيز → محملة → عهدة مقبولة → منطلقة → في محطة/مقطع → وصلت → تحت المصالحة → مغلقة تشغيليًا`.

فروع: متوقفة، معطلة، مسار متغير، عادت للمخزن، حوادث/فروقات مفتوحة.

### 5.5 محاولة التسليم

`مجدولة → خرجت للتسليم → وصل المنفذ → تحقق من المستلم → تسليم كامل/جزئي`.

الفشل ينتقل إلى: `تعذر موثق → قرار إعادة محاولة/حجز/RTO/تحويل`. لا يعاد توصيف المحاولة الأولى أو حذفها.

### 5.6 RTO

`قرار إرجاع مسبب → مسار عكسي محدد → قبول عهدة الإرجاع → نقل عكسي → استلام فرع/مخزن المصدر → تسليم للمرسل أو معالجة أخرى → إغلاق RTO`.

يلزم تمييزه عن مرتجع الترحيل للمخزن قبل بدء الخدمة، وعن التحويل إلى رحلة بديلة.

### 5.7 المطالبة التشغيلية

`واقعة مسجلة → أدلة أولية → تجميد/حجز المتأثر عند الحاجة → مراجعة سلسلة العهدة → تحديد نطاق الضرر المثبت → قرار تشغيلي → إحالة الأثر المالي إلى 05 → إغلاق/متابعة معلنة`.

المطالبة قد تبقى مفتوحة بعد وصول بقية وحدات البوليصة؛ سياسة أثرها على إغلاق البوليصة تحتاج قرار مالك.

### 5.8 الراكب/التذكرة/المقطع

- الحجز: مؤقت، مثبت، ملغى، عدم حضور.
- التذكرة: صادرة، مستخدمة جزئيًا حسب المقاطع، مكتملة الاستخدام، ملغاة/مستردة وفق قرار 05.
- الراكب في الرحلة: متوقع، صعد، حُوّل، نزل، نزل مبكرًا، لم يحضر.
- الرحلة: مخططة، مفتوحة للصعود، منطلقة، في مقطع، وصلت، تحت المصالحة، مغلقة تشغيليًا.

### 5.9 دفتر البوالص الورقي — إضافة تصحيحية بلا ID جديد

- الدفتر: نطاق من `50` ورقة يبدأ من إحدى البدايات `1 / 51 / 101 / 151 ...`.
- عهدة الدفتر: `غير مسلّم/مسجل → بعهدة طرف تشغيلي → تحت المصالحة → مردود/مغلق تشغيليًا` بحسب الإجراء المعتمد، دون تعريف مالي جديد.
- حالة الورقة داخل الدفتر: `متاحة → مستخدمة` أو `متاحة → ملغاة`؛ الورقة المستخدمة أو الملغاة لا تعود متاحة.
- كل ورقة تحتفظ برقمها الورقي وبعلاقتها برقم النظام عند الاستخدام.
- كل رقم داخل نطاق الدفتر يجب أن يكون مفسر الحالة عند المصالحة؛ لا يسمح بورقة خارج النطاق ولا بتجاوز نهاية الدفتر.

قواعد Handoff الحاكمة:

1. على 05 استهلاك خريطة المراحل في §4، وبخاصة الفرق بين التخصيص والتحميل والتنفيذ الفعلي.
2. على 05 استهلاك مصفوفة الاستثناءات §6 لتحديد الأثر المالي دون إعادة تعريف الواقعة التشغيلية.
3. على 05 استهلاك P04-01..P04-16 مع حفظ `مصرح/متحقق/فعلي` حيث ينطبق.
4. التسليم التشغيلي لا يساوي التحصيل، وRTO/المطالبة حدثان مرتبطان بأصل البوليصة لكن أثرهما المالي ملك 05.
5. الجزء المنفذ فعليًا وحالة كل Leg/وحدة هما مدخلان إلى تكلفة الناقل/التسوية؛ لا يقرر 04 أن ذلك وحده هو قاعدة الدفع أو الاستحقاق.
6. لا يجوز ل05 أن ينسب إلى 04 أي سعر أو نسبة أو قيد أو قرار مسؤولية مالية غير موجود.

ولا يجوز لـ05 اعتبار ما يلي محسومًا من 04:

- تعريف الخفيف/المتوسط/الثقيل وحدوده.
- عدد المحاولات المجانية أو رسوم RTO.
- نسبة مسؤولية تلف/نقص بلا تحقيق.
- أثر المطالبة المفتوحة على الإغلاق المالي.
- أي خصم أو تعويض أو استرداد.
- أي نسبة عمولة أو سعر ناقل أو قاعدة تسوية محاسبية.

## 10. Handoff إلى الفريق 07 وOffline

### 10.1 ما يحتاج قرار/مواصفة من 07

- هوية المستخدم/الجهاز/الشركة/الفرع لكل حدث.
- سياسة OTP/توقيع/صورة هوية/POD لكل نوع خدمة ودولة/منطقة.
- مصدر GPS: هاتف/جهاز مركبة، دقته، زمنه، واكتشاف التلاعب.
- الفرق بين التقاط حي ومرفق من المعرض وقوة كل دليل.
- حماية الأدلة في الجهاز والتخزين والاحتفاظ والحذف والتدقيق.
- أقل بيانات تُعرض للسائق/المندوب/العميل.
- صلاحيات العرض والتنفيذ والاعتماد السياقي.
- envelope لكل Action مرشح للصف دون اتصال، وإعادة التفويض عند replay.

### 10.2 تصنيف الأفعال دون اتصال

القاعدة اللغوية والحاكمة في هذه المسودة هي:

`ELIGIBLE CATEGORY DOES NOT MEAN ACTION AUTHORITY`

أي تشابه مع فئة عامة مسموح بدراستها في R-012 لا يمنح الفعل سلطة تنفيذ. ما لم يوجد عقد Action فعلي يثبت الهوية والـenvelope والنسخة/التعارض وإعادة التفويض، يكون الحكم:

`OFFLINE WRITE = DENY/UNRESOLVED`

| الفعل | مطابق لفئة عامة في R-012؟ | الدليل الخاص بالفعل/envelope | الحكم في هذه الجولة |
|---|---|---|---|
| حفظ/تعديل مسودة طلب تشغيلية | فئة مرشحة فقط | لا عقد Action مثبت في المراجع المستهلكة | `OFFLINE WRITE = DENY/UNRESOLVED` |
| التقاط Scan/حدث append-only | فئة مرشحة فقط | لا إثبات كامل للهوية والنسخة والتعارض | `OFFLINE WRITE = DENY/UNRESOLVED` |
| قبول/نقل عهدة | فئة مرشحة فقط إذا replay-safe؛ لا دمج صامت | لا عقد خاص مثبت | `OFFLINE WRITE = DENY/UNRESOLVED` |
| تسجيل وصول/تسليم/تعذر | فئة مرشحة ضمن capture محدود | لا عقد خاص مثبت | `OFFLINE WRITE = DENY/UNRESOLVED` |
| التقاط تحصيل كأمر معلق | R-012 يذكر capture ضمن شروط | لا envelope خاص مثبت | `OFFLINE WRITE = DENY/UNRESOLVED` |
| تجهيز صورة/مرفق للرفع | فئة مرشحة وفق سياسة المرفقات | سياسة الحساسية/التخزين غير محسومة | `OFFLINE WRITE = DENY/UNRESOLVED` |
| إصدار رقم بوليصة/تذكرة رسمي غير قابل للعكس | لا | إجراء نهائي | `OFFLINE WRITE = DENY/UNRESOLVED` |
| اعتماد ترحيل/استثناء/حجز أو تحرير حساس | لا، جهة الخادم حاكمة | إجراء موافقة | `OFFLINE WRITE = DENY/UNRESOLVED` |
| إغلاق رحلة/عهدة/بوليصة | لا يوجد إثبات replay-safe خاص | حالة تجميعية حساسة | `OFFLINE WRITE = DENY/UNRESOLVED` |
| تسوية/ترحيل محاسبي/عكس | ممنوع دون اتصال | مالي حاكم | `OFFLINE WRITE = DENY/UNRESOLVED` |

النتيجة: لا يوجد فعل في هذه المسودة مصنف كـQueue مسموح. توجد فقط فئات مرشحة للتحليل؛ ولا تتغير أي Action إلى سماح حتى يثبت عقدها الفعلي وتتحقق شروط R-012 ويعاد التفويض على حالة الخادم.

## 13. أسئلة المالك

8. هل التعيين الآلي للمندوب/السائق مفعل، وما عوامل الأولوية: القرب، الخط، السعة، الثقة أم التكلفة؟
9. هل يجوز للسائق إنشاء طلب منقول من الطريق فقط، أم إصدار بوليصة لفئات مخولة؟

11. ما POD الإلزامي لكل خدمة/منطقة: OTP، توقيع، صورة، هوية، وزن/ختم؟
12. ما سماح فرق الوزن/الكمية الذي ينشئ تنبيهًا أو حجزًا أو مطالبة؟
13. ما الحد الأدنى لإغلاق رحلة ركاب عند وجود راكب مفقود الحدث أو تحويل غير مقفل؟
14. هل تبديل رأس القاطرة أو المقطورة يتطلب قبول عهدة جديدًا أم تعديل مورد فقط؟ توصية التشغيل: حدث انتقال/إسناد مدقق.
