# TransportERP — نموذج المنصة والمجالات التشغيلي

**الإصدار:** P1-Operating-Model-2026-08  
**الحالة:** خط أساس تنفيذي منضبط؛ لا يمثل إغلاق عقود W1/W2/W3 ولا تفويضًا نهائيًا.  
**قاعدة الأدلة:** لا تتحول أي خانة إلى Migration أو API أو سلوك إلزامي إلا بعد أن تكون مثبتة بمرجع رسمي، أو بقرار مالك موثق، أو بدليل تنفيذ داخل المستودع.

## 1. الغرض والنطاق

يحوّل هذا النموذج مصفوفة المطابقة المؤسسية والكراسة الأم إلى بنية تشغيلية قابلة للتحويل إلى عقود. وهو يحدد ما يجب أن يوجد في كل مجال من **كيانات، حالات، تهيئة، مدخلات، مخرجات، صلاحيات، تدقيق، وتزامن**، مع الفصل بين ما تثبته مراجع الشركات الكبرى وما حدده مالك TransportERP محليًا.

تثبت مراجع Microsoft وOracle الحاجة إلى فصل الطلب أو الشحنة عن التخطيط وبناء الحمولة والمسار والتعرفة ومزود النقل، وإلى وجود REST APIs وأدلة تنفيذ وإصدارات وقاموس بيانات في منصة النقل المؤسسية [1] [2]. وتثبت مراجع Samsara وOnfleet وAmadeus أن التشغيل المؤسسي يمتد إلى GPS والصيانة والإرسال وإثبات التسليم والتذاكر ذات حالات التغيير والاسترداد والإلغاء [3] [4] [5]. أما طرق الدفع المختلطة، البوالص متعددة الأصناف، الجمارك المحلية، البحث بالاسم، وتوافق الخصم فهي **متطلبات مالك** وليست استنتاجًا من تلك الشركات.

## 2. نموذج المنصة الحاكم

### 2.1 طبقات النطاق المؤسسي

يجب أن يكون لكل سجل تشغيلي أو مالي نطاق صريح، لا قيمة ضمنية مستنتجة من المستخدم الحالي. يحدد النطاق الشركة، والفرع، والكيان القانوني عند الحاجة، ووحدة التشغيل، ثم يطبق الصلاحيات على هذا النطاق. وتبقى الإعدادات في أربع طبقات: إعدادات عامة للمنصة، إعدادات الشركة، إعدادات الفرع، وإعدادات المستخدم أو الجهاز، مع قاعدة أولوية موثقة تمنع إعدادًا أدنى من كسر قاعدة أعلى.

| الطبقة | الغرض | أمثلة | قاعدة العزل |
|---|---|---|---|
| المنصة | قواعد مشتركة لا تعتمد على شركة واحدة | أنواع المستندات، حالات النظام، قوالب التدقيق، أنواع المزامنة | لا تحتوي مبالغ أو أرصدة تخص شركة بعينها |
| الشركة/الكيان القانوني | الملكية والعملة والتقويم ودليل الحسابات والسياسات | `Company`, `LegalEntity`, `Ledger`, `Currency`, `FiscalCalendar` | لا يرى المستخدم سجلًا خارج نطاقه إلا بصلاحية مجمعة |
| الفرع/وحدة التشغيل | التنفيذ المحلي والموارد ونقاط الخدمة | `Branch`, `Depot`, `CashBox`, `Route`, `ServicePoint` | الفرع يرى بياناته، والتجميع يحتاج صلاحية تقارير |
| المستخدم/الجهاز | التفضيلات وحالة العمل دون اتصال | `User`, `Role`, `Device`, `SyncCursor` | لا تتحول التفضيلات إلى صلاحيات خادم |

### 2.2 الخدمات المشتركة

الخدمات التالية مشتركة بين المجالات ولا يجوز إعادة تنفيذها بصورة منفصلة داخل كل وحدة: الهوية والصلاحيات، النطاق المؤسسي، الترقيم، المرفقات، الإشعارات، الموافقات، سجل التدقيق، البحث الموحد، العملات والفترات، التزامن، سجل الإصدارات، والتقارير. يعتمد كل مستند رقمًا داخليًا ثابتًا ومعرفًا خارجيًا قابلًا للعرض، ويحتفظ بسجل تغييرات لا يسمح بتعديل الأثر بعد الإغلاق إلا عبر إصدار جديد أو طلب تغيير معتمد.

| الخدمة المشتركة | الحد الأدنى التشغيلي | الدليل/القرار | حالة P1 |
|---|---|---|---|
| الهوية والصلاحيات | مستخدم، دور، صلاحية فعل، نطاق شركة/فرع، فصل واجبات | نموذج المؤسسة + متطلبات المالك | W1/W2/W3 مفتوحة |
| التدقيق | من أنشأ/عدل/اعتمد/رحّل/ألغى، قبل وبعد، الزمن والجهاز | نمط مؤسسي + كراسة المالك | يحتاج عقدًا واختبارًا |
| الموافقات | طلب، مستويات، قرار، سبب، زمن استجابة، تصعيد | متطلب الخصم والتشغيل | يحتاج قواعد محلية |
| المرفقات | ملف، نوع، نسخة، Hash، مستند مرتبط، صلاحية عرض | Oracle GTM/OTM + متطلبات الجمارك | يحتاج سياسة احتفاظ |
| البحث الموحد | اسم طبيعي، مرجع بوليصة/تذكرة/سند، رقم هاتف أو معرف | متطلب المالك للسداد | يحتاج فهارس واختبار مطابقة |
| الإصدارات | نسخة مستند، سبب التغيير، ارتباط بالإصدار السابق | متطلب تعديل ما بعد الإغلاق | يجب ربطه بالتدقيق |
| Offline/Online | طابور عملية، Hash، نسخة، إعادة محاولة، تعارض، قرار حل | متطلب المالك؛ `SyncOperations` جديد | W1-P1-017 مفتوح |

## 4. قواعد الحالة المشتركة

لا تستخدم المجالات المختلفة أسماء حالات متعارضة لنفس المعنى. يجب أن يعرّف قاموس المنصة حالات عامة قابلة للتخصيص مع انتقالات مسموحة حسب نوع المستند. لا يجوز أن يؤدي تغيير حالة في الهاتف دون اتصال إلى ترحيل مالي نهائي ما لم تنص سياسة الكيان على ذلك ويُحفظ أثر المزامنة.

| الفئة | حالات الحد الأدنى | الانتقالات الممنوعة |
|---|---|---|
| مستند تشغيلي | `Draft → Validated → Approved → InProgress → Completed → Closed` | إكمال قبل التحقق؛ إغلاق مع رصيد أو عنصر غير مسلّم |
| مالي | `Draft → Checked → Approved → Posted → Settled → Reversed` | تعديل بعد الترحيل دون عكس أو إصدار تغيير؛ ترحيل فترة مغلقة |
| تذكرة/حجز | `Held → Issued → Boarded → Changed/Refunded/Voided` | إصدار بلا تحقق هوية/مقعد/دفع وفق السياسة |
| جمارك/منع | `PendingCheck → Hold → Released/Rejected` | ترحيل صنف محظور؛ Release بلا سبب أو صلاحية |
| مزامنة | `Queued → Sending → Succeeded/Failed/Conflict/Rejected → Resolved`؛ تبقى العملية `FAILED` أثناء إعادة المحاولة مع تحديث `RetryCount` و`NextRetryAt` ثم تعود إلى `SENDING` بعد Backoff | حذف عملية فاشلة دون أثر؛ تطبيق نفس العملية مرتين دون idempotency؛ استخدام `RETRIED` كحالة مستقلة |

## 5. قواعد القرار المحلية غير المفترضة

الآتي مثبت كاحتياج من المالك لكنه لا يملك قيمة تنفيذية نهائية حتى يصدر اعتماد محدد. لذلك يظهر في العقود بوصفه `OWNER_DECISION_REQUIRED` ولا يدفن داخل كود أو Migration.

| القرار | القيمة الحالية | المطلوب لاعتماده |
|---|---|---|
| قائمة الممنوع والمقيد | علاجات، مخدرات، وأصناف أخرى يحددها المالك/الجهة | قائمة رموز، نوع القيد، رسالة، منع افتراضي، مسار تجاوز |
| صلاحيات التجاوز | غير محددة | دور/صلاحية، سبب إلزامي، اعتماد ثانٍ عند الحاجة، تدقيق |
| أولوية التسعير | السعر/الوزن/الحجم/النوع/السرعة مع آلي/يدوي/اقتراح | ترتيب عوامل، طريقة فض التعارض، حد الانحراف عن الاقتراح |
| قواعد الجمارك المحلية | جمارك محتملة على المسارات الداخلية والدولية | المسار، الصنف، الجهة، المستند، الرسم، حالة Hold/Release |
| تاريخ الاستحقاق | غير محدد للبوالص والتذاكر | قاعدة حسب الدفع والجهة ونقطة التحصيل والاتفاق |
| أساس نسب كشف الترحيل | غير محسوم | قبل الخصم أو بعده، والتقريب، ومعالجة الإلغاء والاسترداد |
| إشعار توافق الخصم | غير محدد | القناة، المدة، التصعيد، صلاحية الرفض، الأثر عند عدم الرد |
| حد الاعتماد الثالث | غير محدد | نسبة/مبلغ، جهة الاعتماد، مسار استثنائي، تدقيق |

## 6. معايير تحويل النموذج إلى عقود

قبل أن يغلق أي مجال، يجب أن يربط كل كيان بجدول W1 أو يبرر دمجه في كيان قائم، ويربط كل فعل W2 بحالة قبلية وانتقال وحماية idempotency، ويربط كل شاشة W3 بالحقول والحالات والأفعال والصلاحيات والسياسات غير المتصلة. يجب أيضًا توفير اختبار قبول يثبت التدفق الطبيعي، الرفض، التكرار، التزامن، التدقيق، ونطاق الشركة والفرع.

| بوابة | دليل الإغلاق المطلوب | مالك الدليل |
|---|---|---|
| نموذج البيانات | عقد W1 مكتمل ومراجع مع PK/FK/Indexes/Lifecycle/Migration | قائد البيانات/المعماري |
| الأفعال | عقد W2 مكتمل مع DTO وحالات وأخطاء وصلاحيات وOffline | قائد API |
| الشاشات | عقد W3 مكتمل مع Wireframe RTL وحقول وحالات وأفعال | قائد UX/المالك |
| التشغيل | اختبارات قبول ناجحة مع بيانات معزولة حسب الشركة/الفرع | QA والمالك |
| المزامنة | اختبارات idempotency والتعارض وإعادة المحاولة والتدقيق | قائد المنصة |
| المحاسبة | تحقق تركيب الحساب والفترة والعملة والتسوية | قائد المالية |
