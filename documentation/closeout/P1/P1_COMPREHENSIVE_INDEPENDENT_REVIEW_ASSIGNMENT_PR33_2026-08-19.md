## 3. نطاق المراجعة الشامل

### 3.1 نطاق التغيير في PR

يجب فحص diff كامل بين فرع PR والفرع `master`، وتحديد كل ملف مضاف أو معدل أو محذوف. يجب التأكد من أن التغييرات محصورة في نطاق إغلاق CA-RR3-01 وCA-RR3-02 وCA-RR3-03 وأدلة المراجعة المرتبطة، وألا توجد تغييرات جانبية غير مبررة.

### 3.2 النطاق الوظيفي والتقني

يشمل الفحص `AuditEventService` و`SyncOperationService` و`ConflictCase` و`TransportErpDbContext` وMigrations ومسارات API واختبارات PostgreSQL واختبارات HTTP/JWT. ويجب التحقق من استمرار المتطلبات التالية دون تراجع:

| المجال | نقاط التحقق |
|---|---|
| AuditEvent | append-only على مستوى PostgreSQL، Hash-chain canonical، عزل stream/company/branch، القراءة المصفاة، وتسجيل النتيجة والسبب |
| SyncOperation | idempotency، دورة الحياة، بقاء العملية `FAILED` عند الفشل القابل لإعادة المحاولة، تحديث `RetryCount` و`NextRetryAt`، وعدم استخدام `RETRIED` |
| ConflictCase | جدول وكيان مستقلان، علاقة صحيحة مع `SyncOperation`، وقابلية القراءة والتتبع |
| الصلاحيات | JWT Bearer فعلي، claims، الشركة والفرع والجهاز، رفض غير الموثق وغير المصرح له |
| PostgreSQL | تطبيق Migrations، إعادة التطبيق، التوازي، القيود، trigger append-only، وعدم وجود سباق أو اعتماد على ترتيب غير موثق |
| الاختبارات | التشغيل الافتراضي بلا فلتر، الاختبارات الوظيفية، HTTP، التوازي، الفشل الأمني، وعزل البيانات |
| البناء | Clean/Build موحدان، 0 Warning، 0 Error، وعدم وجود تحذير مخفي أو فرق بين artifact وإعادة البناء |
| التتبع | نفس SHA في PR والطلب والتقرير والmanifest وسجلات الأدلة، مع وسم المراجع التاريخية بوضوح |

## 5. معايير القرار

يصدر الفريق **`PASS`** فقط عند تحقق جميع الشروط الآتية: سلامة diff، إغلاق كل ملاحظات PR، نجاح الاختبارات المطلوبة على نسخة PR، نجاح Clean/Build دون تحذيرات أو أخطاء، سلامة PostgreSQL وMigrations، اكتمال فحص API والأمن، تطابق traceability وSHA-256، وعدم وجود ملاحظة حرجة أو غير مفسرة.

يصدر الفريق **`FAIL`** عند وجود أي فشل اختبار، أو تحذير غير مفسر، أو عدم تطابق SHA، أو فجوة في الأمن أو العزل أو المزامنة أو قاعدة البيانات، أو تغيير خارج النطاق، أو نقص في الأدلة، أو تعارض في قرار الحوكمة. يكون القرار واحدًا فقط ولا تُستخدم صيغة `PASS_WITH_NOTES` أو قرار مركب.

> **قاعدة حاكمة:** لا دمج قبل قرار `PASS` مستقل وموثق من هذا التكليف، حتى لو كانت حالة PR في GitHub `CLEAN`.
