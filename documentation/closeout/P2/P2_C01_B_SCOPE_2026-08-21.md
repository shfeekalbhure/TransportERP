## 1. Purpose

P2-C01-B realizes the payment-plan, actual collection, controlled collection reversal, financial-status derivation, and finance cross-reference boundary for an already created Waybill. It extends the closed P2-C01-A foundation without reopening A's draft, approval, numbering, or schema decisions.

## 2. Governing W1 contracts

- `W1-P2C01-002 — Waybill`: FinancialStatus is independent from operational status and is derived, not manually edited.
- `W1-P2C01-007 — PaymentPlanLine`: payer role, method, amount/percent, due trigger/date and lifecycle.
- `W1-P2C01-008 — CollectionTransaction`: immutable accepted collection with ClientOperationId and reversal reference.
- `W1-P2C01-023 — FinancialLink`: append-only cross-reference to P1 voucher/journal/document when a finance document exists.

## 3. Governing W2 actions

- `W2-P2C01-011 — SetPaymentPlan` — `PUT /api/v1/waybills/{waybillId}/payment-plan`.
- `W2-P2C01-012 — RecordCollection` — `POST /api/v1/waybills/{waybillId}/collections`.
- `W2-P2C01-013 — ReverseCollection` — `POST /api/v1/collections/{collectionId}:reverse`.

Existing A actions remain inherited and are not reopened.

## 4. Governing W3 screens

- `SHP-009 — services/pricing detail`: only the B-authorized payment-plan/pricing interaction; no hard-coded accounting accounts.
- `SHP-010 — Waybill Payment Plan`.
- `SHP-011 — Waybill Collections`.
- `SHP-012 — Payment Status and Remaining`.

## 5. In scope

- Payment plan lines with split payer and mixed methods.
- Plan validation against payable amount/policy.
- Actual collection with explicit currency and exchange-rate snapshot fields authorized by W1/W0-5.
- `ClientOperationId` idempotency for collection acceptance.
- Accepted collection immutability.
- Reversal as a separate referenced transaction; no delete/update of accepted monetary history.
- Financial status derived from accepted net collections: unpaid / partial / paid / overpaid as governing policy resolves.
- Company/Branch isolation and collector identity.
- Audit of plan changes, collection acceptance and reversal.
- Optional `FinancialLink` to existing P1 finance documents; this phase does not invent posting or revenue-recognition policy.
- Desktop/API surfaces required by SHP-009..SHP-012 only.
- Additive PostgreSQL migration for B only.

## 6. Explicitly out of scope

P2-C01-B MUST NOT implement:

- Item Release or Allocation.
- Trip / TripStop / Manifest / ManifestLine / Load.
- Movement runtime, Arrival, Warehouse or Transit.
- Customs clearance runtime.
- Delivery / POD / COD delivery workflow beyond collection semantics explicitly authorized here.
- Commissions, TripSettlement, revenue posting, financial close/reopen.
- GPS/Fleet, ticketing, maintenance or HR runtime.

## 7. Financial rules

1. `OperationalStatus` and `FinancialStatus` remain separate.
2. Payment plan is not actual cash movement.
3. Accepted collection is immutable; correction occurs through `ReverseCollection` with reason and reference.
4. No physical delete of accepted collection or finance link.
5. Every monetary DTO must preserve currency identity; exchange rate used for an accepted transaction is a historical snapshot and cannot be silently recomputed later.
6. Collection retries with the same `ClientOperationId` return the same accepted outcome and cannot duplicate money.
7. Financial status is derived from ledger totals, never directly editable by UI.
8. P1 posting/reversal/accounting contracts govern any created voucher/journal reference; B does not bypass them.
