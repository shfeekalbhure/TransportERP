# Physical Schema P1 — PostgreSQL 18.6

**الحالة:** `IMPLEMENTATION_BASELINE`  
**قاعدة البيانات:** PostgreSQL 18.6  
**النطاق:** عقود W1 وW2 وW3 المغلقة لـP1 فقط  
**المخطط:** `transport_erp`

## قاعدة التصميم

هذا المخطط هو أول تحويل فيزيائي لعقود P1 بعد اعتماد PostgreSQL 18.6. لا يضيف جداول تشغيلية للنقل أو الشحن أو السفريات قبل إغلاق عقود الإصدارات اللاحقة. كل عمود أساسي أدناه مصدره عقد W1، وكل قيد دورة حياة أو idempotency مصدره W1/W2. الحقول التي تمثل أطفالًا في العقد، مثل `JournalEntry.Lines` وتعيينات الصلاحيات، لها جداول تابعة ضرورية للعلاقة، وتحتاج مراجعة عقدية تفصيلية قبل توسيعها خارج P1.

## قواعد PostgreSQL العامة

يستخدم المخطط `uuid` للمفاتيح، و`numeric(19,4)` للمبالغ، و`numeric(19,8)` لمعدلات الصرف، و`timestamptz` للأوقات، و`bytea` لـ`RowVersion`. تُستخدم قيود `CHECK` للحالات بدل PostgreSQL enum حتى تبقى تحديثات الحالة صريحة عبر Migration ولا تنشئ اعتمادًا خفيًا على نوع مخصص.

تُستخدم فهارس فريدة جزئية حيث نص العقد على `WHERE DeletedAt IS NULL` أو على القيم غير الفارغة. وتُستخدم مفاتيح مركبة `(BranchId, CompanyId)` في الجداول التي يجب فيها إثبات انتماء الفرع للشركة.

## قيود لا تُخفى داخل المخطط

`ReferenceId` في القيود والسندات مرجع polymorphic حسب العقد، لذلك لا يُنشأ له Foreign Key زائف إلى جدول غير محدد. و`CashBoxId` يحتفظ به كمعرف nullable لأن عقد P1 يشير إلى CashBox دون أن يقدم عقد كيان مستقل له؛ إنشاء جدول CashBox مؤجل إلى عقده الصريح.

تُحفظ قيم JSON في P1 كنص `text` لأن W1 يحدد `ValueJson:text` و`PayloadJson:text`، ولا يغير المخطط هذا النوع إلى `jsonb` دون إدارة تغيير موثقة. يمكن إضافة فهرسة JSON لاحقًا عند اعتماد عقد البحث والهيكل.

## Children ذات العقد غير المفصل

يتطلب `JournalEntry.Lines:child array` جدولًا تابعًا. أُدرجت الحقول الأساسية اللازمة لضمان القيد المتوازن وربط الحساب والبعد المالي، لكن عقد DTO التفصيلي لأسطر القيد لم يُغلق في سجل W1. لذلك تُوسم هذه النقطة في الاختبارات والمراجعة بأنها `CONTRACT_DETAIL_PENDING`، ولا يجوز توسيعها بإضافات تشغيلية غير موثقة.

تُعامل تعيينات الأدوار والصلاحيات كجداول تابعة مستقلة لأن W1-003 يصرح بوجود `RoleAssignments` و`UserOverrides`. تفاصيل نطاق الشركة/الفرع للتعيين تحتاج أن تظل في طبقة سياسة الصلاحيات إلى أن يغلق عقدها التفصيلي.

## بوابات القبول

قبل استخدام Migration على أي بيئة مشتركة يجب نجاح: بناء الحل، إنشاء قاعدة اختبار فارغة، تطبيق Migration من الصفر، إعادة تطبيقها دون تغيير، اختبار قيود الشركة/الفرع والفهارس الفريدة، اختبار append-only لسجل التدقيق، اختبار uniqueness المركب للمزامنة، واختبار rollback على نسخة اختبارية.
